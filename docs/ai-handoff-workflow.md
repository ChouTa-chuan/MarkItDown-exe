# AI 輪替作業與交接工作流

流程版本：**1.0**；更新：**2026-11-12（台北）**。本流程適用於同事、Codex、其他 AI 與新的 session 輪替接手，與程式／架構版號分開維護。

交接依據是 **GitHub 上已推送的指定分支／PR、交接紀錄與驗證證據**。一般情況下使用者只需指定要接手的分支或 PR，不需要轉貼上一個 AI 的全部回覆。

## 1. 固定入口與文件責任

| 位置 | 責任 |
| --- | --- |
| [AGENTS.md](../AGENTS.md) | 每位接手者必讀的工作規則及本流程入口 |
| [PROJECT_HANDOFF.md](../PROJECT_HANDOFF.md) | 專案背景、規劃、目前實作／驗證、限制與整體接續方向 |
| [交接索引](handoffs/README.md) | 當前所讀分支可見的各次交接，指向具體分支／PR與紀錄 |
| [交接範本](handoffs/TEMPLATE.md) | 每次告一段落的統一欄位；填完另存新檔，不能直接改範本當紀錄 |
| [開發紀錄](development-records/README.md)、[CHANGELOG](../CHANGELOG.md) | 過程／證據與精簡版本差異，避免把長期歷史全部塞進交接摘要 |
| [.github/pull_request_template.md](../.github/pull_request_template.md) | PR 必須引用分支、提交、驗證與交接紀錄 |

索引只代表**該分支**可見的紀錄。尚未合併的 PR 不會自動出現在 `main` 的文件；不同分支的「最新一筆」也不能當成整個專案唯一最新狀態。

## 2. 接手時先做的事

1. 確認使用者指定的 repo、分支／PR與任務。若只指定 PR，就查出其 head 分支、base 分支、目前 head SHA與是否已合併；不能只讀 `main`。
2. 檢查本機工作目錄、實際分支及未提交變更，讀取遠端最新 refs。已有他人變更就保留，必要時使用新的 worktree／checkout 隔離。
3. 閱讀**目標分支版本**的 AGENTS、PROJECT_HANDOFF、本流程、交接索引、最近交接及其證據。查最近提交與差異，區分內容提交、測試來源、PR 暫時 merge commit及純文件提交。
4. 核對「已完成／未完成／阻擋／下一步」，確認上個 AI 的結果已推送、證據仍可取得，且沒有把 planned／skip／expected failure當成功。
5. 使用者已指定分支且範圍清楚就直接接續。只有一個明確待接手目標可自行核對；多個分支工作不同、無法判斷意圖時，才請使用者指定分支或 PR。
6. 獨立工作開新分支。若承接尚未合併的 PR，就寫明父分支／父 PR、自己的 PR 目標及合併順序，不把父 PR 的整包改動當成本次新增成果。

目前工作規則為工作分支＋PR，**不直接推送 `main`；合併由使用者另行指示**。不自行推送另一個 AI 的工作分支，也不丟棄其未提交內容。

## 3. 作業期間如何自主推進

- 既有授權範圍內的閱讀、檢查、實作、必要驗證、文件維護、提交、推送自己的工作分支與建立 PR，可自行完成，不逐項要求使用者重複確認。
- 依變更影響選驗證。純文件改動查路徑、規則、來源與連結即可；不要為文件更新重跑完整 Windows／OCR。功能變更則補必要測試及真正退出結果。
- 環境、工具權限與網路政策逐個 session 核對。其他 AI 曾安裝套件、下載 artifact 或開過頁面，不代表本環境也已有該能力。
- 確有權限／平台阻擋時，寫具體錯誤及最小待辦；其他不受影響的工作繼續。需要使用者決定的事項先做成可審閱方案，不用提問取代已授權準備工作。
- 授權、刪除、更改打包方式、發行及合併等界線依 AGENTS 與使用者新指示處理；更新本工作流不會自行擴大權限。

## 4. 每次告一段落必須留下的四組資料

### A. 工作分支與 PR

寫明 repo、工作分支、base 分支／base SHA、PR 連結與狀態、父 PR／依賴分支、內容提交。尚未開 PR、未推送或仍有未提交內容要明說。

有工具權限就自行建立 PR；無法建立時，先推送自己的分支，留下**已填 base／head 的比較或建立 PR 連結**與具體限制。不能把比較網址寫成已建立的 PR。

### B. 完成事項、測試結果及對應提交

列實際完成內容與改動範圍。測試要標示命令／CI run、source SHA、平台／工具版本、run／pass／failure／error／skip／expected failure及真正 process exit；證據寫 repo 路徑／hash／保存期限。

沒跑就寫「未執行」及原因，繼承前次結果要標「既有證據」；不能把另一輪測試歸到本次 HEAD。PR 的暫時 merge SHA、分支 head、候選包 source SHA各自記錄。最後的純交接文件提交可在最終回覆列出，內容／測試提交固定引用已有 SHA，避免在檔案裡填自己的最終 commit 造成循環。

### C. 未完成事項、阻擋原因與下一步

分開列可立即做的工作、等待使用者決策、平台／權限阻擋及有期限的報告。下一步要有優先順序、第一個可執行動作、預期產物與完成條件，不能只寫「繼續優化」。

仍可立即進行的已授權工作，不要因另一件待決事項全部停下；相依工作若必須等父 PR 合併，寫明依賴，避免下一個 AI 重做或直接改 `main`。

### D. 新增需求或工作規則

記錄日期、來源（使用者明確指示／已核准提案／待確認建議）與影響。確認過的新規則同步 AGENTS、交接指南及本流程的相關段落；尚未核准的授權或打包建議保持待定。

四組欄位都必須填。沒有新增需求、沒有測試或沒有 PR 時，填明確狀態與原因，不留空讓下一位猜。

## 5. 收工／交棒步驟

1. 核對 diff及分支範圍，完成必要驗證，保存原始失敗與結果；不提交秘密、使用者文件、venv或cache。
2. 提交本次內容，推送工作分支。記錄內容／測試 SHA；檢查遠端 head 是否一致。有衝突或推送失敗就如實記錄，不宣稱已同步。
3. 建立或更新 PR；只核對自己的目標，不在交棒時自行合併 `main`。
4. 複製[範本](handoffs/TEMPLATE.md)，另存 `docs/handoffs/YYYY-MM-DD-AI-主題.md`，同日多階段用新的唯一名稱；更新[索引](handoffs/README.md)，最近交接放上方。
5. 更新 PROJECT_HANDOFF 的當前交接入口／相關狀態，以及受到影響的 CHANGELOG、開發紀錄、進度與驗證資料；不為了湊更新改里程碑。CI仍在跑就寫 running，出結果後另存補記並修正目前索引狀態。
6. 推送交接與文件提交。需要新 PR／CI 時依工具能力處理；原始 run 附件維持不變，修正舊判讀要新增更正並說明原因。
7. 最後回覆提供分支／PR、主要內容及交接提交、交接檔案連結、完成／驗證／阻擋／下一步，以及一句可直接轉交的接手指令。

已推送的舊交接保留。索引與整體指南可持續更新；新的階段另建紀錄並引用前一筆，避免覆寫歷史。只留在聊天、暫存區或未推送工作目錄的內容不算完整交棒；若確實推送不了，寫出可取得的 patch／位置及限制。

## 6. 使用者與下一個 AI 的最短接手指令

> 請接手分支 `xxx`／PR `#123`，先讀該分支的 AGENTS.md、PROJECT_HANDOFF.md 及 docs/handoffs/README.md 最新交接紀錄，再繼續下一項工作。完成後依同一流程更新交接、推送工作分支並提供 PR；不直接推送或自行合併 main。

指定未合併 PR 時，先取該 PR 的 head 及文件，再核對必要的 base／merge 驗證；預設 `main` 的指南只供背景，不能取代工作分支的最新狀態。

進度網站由 `main` 的 Pages workflow 部署。分支紀錄已推送、PR可合併及網站已更新是不同狀態，交接時分別標示。

## 7. 新 AI 如何繼續更新本工作流

發現缺少欄位或步驟時，在工作分支提出具體修正；屬已授權技術／文件改進即可實作並驗證，完成後同步本流程、範本、AGENTS入口及 PROJECT_HANDOFF 第13節，於交接D組記下來源／版本／影響。

有使用者新指示時優先遵從，將舊規則標示為已被取代，不反覆要求確認同一件事。涉及原本需核准的合併、授權、打包或發布決策，先列待確認方案，不透過改文件宣告已獲同意。

流程變動更新下方版本紀錄及 CHANGELOG／開發紀錄；不必為流程文件更新更改應用程式版號或提高產品驗收進度。
