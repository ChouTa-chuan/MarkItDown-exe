# 真實掃描測試包（請印出、掃描後交回）

這份說明給第一次用掃描機或手機的人照做。不需要懂電腦或命令列，照著步驟走就可以。

## 一、先看這裡：你要做的事

1. 把 PDF 印出 9 頁（黑白、實際大小）。
2. 用掃描機或手機，把 9 頁各掃一次或拍一張。
3. 把 9 個檔案交回給我們。

大約 15 分鐘就能完成。

## 二、要準備什麼

- 一台 A4 印表機，以及一般影印紙。
- 一台掃描機，或一支手機（iPhone、Android 都可以）。
- 測試檔：[real-scan-test-kit.pdf](real-scan-test-kit.pdf)，共 9 頁。每頁只有一段文字，內容是我們自己寫的虛構文字，沒有版權或隱私問題。

## 三、列印（請逐項照做）

1. 用 Adobe Reader、Chrome 或 Edge 打開 PDF，按 `Ctrl+P`（Mac 按 `⌘+P`）。
2. **紙張大小**：選 **A4**。
3. **色彩**：選 **黑白**、**灰階**或 **Grayscale**。不要用彩色。
4. **縮放**（英文介面叫 Scale 或 Page Sizing）：選 **「實際大小」**、**「Actual size」** 或 **「100%」**。
   - 在 Adobe Reader 裡，這個選項在列印視窗的「頁面處理」（Page Handling）區，「大小」（Size）選「實際大小」。
   - 在 Chrome 或 Edge 裡，在列印視窗的「縮放」選 100%，或「實際大小」。
   - **不要選「符合頁面」、「適合頁面」或「縮小以符合」（Fit）。** 縮放錯了，小字的大小就不對，測試結果會失準。
5. **雙面列印**：關閉，選「單面」。雙面列印可能會透字到另一面。
6. **省墨、草稿模式**：關閉。
7. 每頁中間只有一小塊文字，其餘都是白色空白，這是正常的，不用擔心。
8. 印完後等墨水乾。不要在紙上寫字、不要摺疊、不要弄濕。

## 四、用掃描機掃描（方式 A）

1. **解析度（dpi）**：選 **300**。
   - dpi 就是掃描的細緻度，數字越大，檔案越大。掃描軟體裡常寫作「解析度」或「Resolution」。
   - 如果選單裡沒有 300，就選最接近而且不低於 300 的選項（例如 350 或 600）。**不要選 150 或 200。**
2. **檔案格式**：JPEG（.jpg）或 PNG（.png）都可以。
3. **關閉自動處理**：把「自動美化」、「自動增強」、「去除雜點」、「自動校正」、「背景清除」等功能關掉，保持原樣。
4. 一頁掃一次，存成一個檔案，檔名依第六節的規則。
5. **如果掃描機只能輸出一個多頁 PDF**，也可以。直接把整份 PDF 交回，不必拆開，我們會自己拆成 9 頁。
6. 紙張歪斜沒關係，不必特地擺正。這正是我們要測的真實情況。

## 五、用手機拍照（方式 B）

1. 把紙平放在桌上，光線要均勻。不要讓窗戶的陰影、手的影子或手機的影子落在紙上。**不要開閃光燈。**
2. 手機要站在紙的正上方，鏡頭與紙面平行。不要斜著拍，否則紙會變成梯形。
3. 整張 A4 都要拍進畫面，四邊各留一點桌面。
4. **不要用 App 自動裁邊、濾鏡或「文件掃描」功能。** 直接用手機原本的相機拍。
5. **照片格式要是 JPEG。**
   - iPhone：到「設定」→「相機」→「格式」，選「最相容」，就會存成 JPEG。或拍完後，在照片中匯出成 JPEG。
   - **不要傳 HEIC 檔**，我們的工具無法讀取。
6. 手機照片通常很大，直接傳原檔就好，我們會自己縮小，不必先處理。

## 六、檔名規則

**每一頁一個檔案，檔名是頁碼加上後綴。** 不論只做一種方式，都要加後綴。

- 用掃描機：`01-scanner.jpg`、`02-scanner.jpg`、……、`09-scanner.jpg`
- 用手機：`01-phone.jpg`、`02-phone.jpg`、……、`09-phone.jpg`
- 副檔名用 `.jpg` 或 `.png` 都可以，同一批最好用同一種。
- 檔名不要加空白，也不要改成其他名稱。
- 如果第二次再用另一種方式做，就用另一個後綴（掃描機用 `-scanner`，手機用 `-phone`），兩次的檔案分開放。
- 如果掃描機給的是多頁 PDF，直接整份交回，檔名不限。

## 八、怎麼交回

1. **優先方式**：把 9 個檔案放進同一個 zip 壓縮檔，上傳。
2. 如果上傳失敗或貼不上去，就分批傳，**每次 3 張**。
3. 檔案大小（以下是估計值，實際大小依機型與設定而不同）：
   - 手機照片：每張約 2 至 5 MB。
   - 掃描機 300 dpi 的 JPEG：每張約 1 至 3 MB。
   - 檔案太大也沒關係，直接傳原檔即可，我們自己處理。
4. **不確定的設定，請寫在訊息裡一起交回**，例如「找不到 300 dpi，選了 350」或「不知道掃描機有沒有自動增強」。不要自己猜。
5. 第二輪的檔案請跟第一輪分開放，檔名保留後綴。

## 以下是給維護者看的，使用者不用讀

### 做了什麼

- [make_scan_kit_pdf.py](make_scan_kit_pdf.py) 把 B3b2 的 9 張合成圖（先逐張核對 samples.json 的 SHA-256，不符即停止）依固定頁序排成 A4 頁面，300 dpi、灰階、圖寬固定 170 mm（2008 px）、置中於 2480×3508 px 白底頁。
- PDF 由 Pillow 的 `save(save_all=True, resolution=300)` 寫出，建立與修改時間固定為 2026-11-21 00:00 UTC，標題固定。同一環境重跑兩次，sha256 相同。
- 產出 PDF：9 頁，A4（595.2 × 841.92 pt），1,797,650 bytes，**sha256 `b781737a3af684bacad22d81a54d47313812021226dbf85ced76fc82e2fdf30b`**，小於 2 MB，放在 repo 內。
- [run_real_scan_evaluation.py](run_real_scan_evaluation.py) 讀取一個資料夾，依檔名取得 01 到 09，比較 v4（rapidocr-onnxruntime 1.4.4 內附權重）與官方 PP-OCRv6 small ONNX。計分沿用 B3b 的 `normalized()`、`edit_distance()`，語言彙總沿用 B3b2 的 `language_totals()`，官方字表與雜湊核對沿用 B3b5 的 `official_check.py`。結果以 `'x'` 模式寫入新檔。
- 檔名規則：腳本以 `--suffix` 指定要評估的那一組（例如 `scanner` 或 `phone`）。腳本本身仍接受無後綴的檔名，但本測試包一律使用後綴。

### 多頁 PDF 的處理（協調者）

使用者若交回整份多頁 PDF，協調者先用 pypdfium2 在 300 dpi 拆成 `01-scanner.png` 至 `09-scanner.png`（或依來源命名），再跑評估腳本。拆頁功能目前不在腳本內，待協調者決定是否加入。

### 前處理實驗（整頁 vs 墨跡裁切）

掃描會有旋轉、邊緣陰影與黑邊，因此比較了兩種做法：
- **page**：整張影像直接辨識（預設）。
- **trim**：以灰階小於 160 的墨跡範圍裁切（保留 2% 邊界），只作對照。

整頁辨識在兩種條件下都較好，且不依賴門檻值。墨跡裁切的限制：門檻 160 在灰底或有陰影的真實掃描上，可能把整頁都當成墨跡，裁切失效。trim 只是對照，不影響預設。

整頁辨識的限制：真實掃描若有黑邊，可能讀出無關的雜訊字，會反映在編輯數上。腳本會保存每頁的辨識文字與行數，方便人工檢查。

### 解析度與 RapidOCR 的縮放

RapidOCR 的 `max_side_len` 設定為 2000（rapidocr-onnxruntime 1.4.4 的 config.yaml）。300 dpi 整頁的長邊為 3508 px，會先縮到約 2000 px，等效約 171 dpi。真實掃描的解析度不同，縮放比例也會不同，因此與乾跑的數字不能直接比較。墨跡裁切後的影像若長邊不超過 2000 px，則不會被縮放。

### 乾跑（不是真實掃描）

乾跑只為確認流程可以走通，並確認分數與 B3b2、B3b5 的同題結果相近。
- **clean**：PDF 以 pypdfium2 在 300 dpi 光柵化。pdfium 的寬度為 2481 px，比生成時的 2480 px 多 1 px。
- **scanlike**：對 clean 每頁套用 B3b3 `degrade_scan.py` 的 `rotate 0.8`、`noise 10`、`jpeg 50`，每頁用固定種子。這只是參數模擬，**不等於真實掃描機或手機的成像**。

| 條件 | 前處理 | v4 編輯數（正確率） | v6 small 編輯數（正確率） |
| --- | --- | ---: | ---: |
| clean | page | 64（96.89%） | 10（99.51%） |
| clean | trim（對照） | 78（96.21%） | 9（99.56%） |
| scanlike | page | 231（88.78%） | 170（91.75%） |
| scanlike | trim（對照） | 339（83.54%） | 288（86.02%） |

參考字數合計 2060，與 B3b2 相同（472＋470＋1118）。clean 的 page 結果與 B3b2 的 v4 合計 72、v6 合計 13 相近，差異來自 300 dpi 光柵化與縮放。逐頁與語言細項見 [dry-run-summary.json](dry-run-summary.json)。

輸入驗證已測試三種錯誤：缺頁、檔名不符規則、只有 `-phone` 後綴而未指定 `--suffix`，三者都會明確停止並說明原因。

### 重現步驟

```bash
# 1. 產生 PDF（需要 repo 內 B3b2 的 samples 與 venv 中的 Pillow）
python make_scan_kit_pdf.py --output <repo 外的路徑>/real-scan-test-kit.pdf
# 2. 評估（需要官方 v6 ONNX 與 inference.yml，見 B3b5 README 的固定 commit）
python run_real_scan_evaluation.py --scan-dir <掃描資料夾> --suffix scanner --mode page \
  --official-v6 <inference.onnx> --official-v6-yml <inference.yml> \
  --chars-dir <新的字表目錄> --output <新的結果 JSON>
```

官方 v6 的 `inference.onnx` 與 `inference.yml` 不放進 repo，請依 B3b5 README 的固定 commit `b8f84f0b…` 下載，並核對 SHA-256 `5435fd74…`（ONNX）與 `ab078671…`（yml）。
