# 真實掃描測試包（給使用者印出、掃描後交回）

這份文件是給使用者照做的。你只需要印表機、掃描機或手機，不需要命令列。

## 一、要準備什麼

- 一台 A4 印表機（黑白即可），以及一張一般影印紙。
- 一台掃描機，或一支手機（拍照即可）。
- 測試檔：[real-scan-test-kit.pdf](real-scan-test-kit.pdf)，共 9 頁，每頁一段文字，都是我們自己寫的虛構內容，沒有版權或隱私問題。

## 二、列印設定

1. 用一般影印紙，A4。
2. **紙張大小選 A4。**
3. **縮放選「實際大小」（100%）。** 不要選「符合頁面」「縮放至可印區域」或任何縮小比例，否則小字會變得不符合測試前提。
4. 色彩：**請用黑白列印**（灰階）。本次測試以黑白為準，彩色版請不要用。
5. 不要開「省墨」或「草稿」模式。
6. 印完後等墨水乾，再進行下一步。

## 三、掃描或拍照方式（二擇一；若兩種都做，請各做一次）

**(A) 掃描機**

- 解析度 **300 dpi**。
- 存檔格式選 **JPEG** 或 **PNG**。
- 關閉「自動美化」「去除雜點」「自動增強」「自動校正」等選項，保持原樣。
- 一頁一檔。若掃描機只能輸出一個多頁 PDF，也可以，直接把整份 PDF 交回，我們會逐頁拆開。

**(B) 手機**

- 把紙平放在桌面，光線均勻，避免陰影落在紙上。
- 手機正上方拍攝，盡量把整張 A4 放進畫面。
- 關閉文件掃描 App 的「自動修正」「濾鏡」「黑白增強」功能，或直接用相機原生拍照。
- 存成 JPEG。

**紙張歪斜不必特別擺正**，這正是我們要測的真實情況。請不要在紙上寫字、不要摺疊或折痕。

## 四、檔名規則

- 依頁序命名為 **`01` 到 `09`**，副檔名 `jpg` 或 `png` 皆可，例如 `01.jpg`、`02.jpg` …… `09.jpg`。
- **一頁一檔**，檔名不要改成其他內容，也不要加空白。
- 第二輪（同一份紙用另一種方式再做一次）時，檔名加上後綴：掃描機為 `01-scanner.jpg` 到 `09-scanner.jpg`，手機為 `01-phone.jpg` 到 `09-phone.jpg`。

## 六、怎麼交回

- 把 9 個檔案直接貼到對話中；或把 9 個檔案打包成一個 zip 再上傳。
- 若檔案太大（單檔超過約 2 MB，或全部超過約 10 MB），請先縮小：掃描機改為 **300 dpi 以內**，JPEG 品質用中等（約 70 至 85）。不要縮小到 150 dpi 以下，會讓小字看不清楚。
- 第二輪的檔案請跟第一輪分開放，檔名保留後綴。

## 七、紙本與頁面

- PDF 總共 9 頁，每頁只有一段文字，不印頁碼、頁尾或 ID，避免干擾結果。
- 每張圖在紙上的寬度為 170 mm，置中。

## 技術說明（給協調者與之後的維護者）

### 做了什麼

- [make_scan_kit_pdf.py](make_scan_kit_pdf.py) 把 B3b2 的 9 張合成圖（SHA-256 先逐張核對 samples.json，不符即停止）依固定頁序排成 A4 頁面，300 dpi，黑白灰階，圖寬固定為 170 mm（2008 px），置中於 2480×3508 px 的白底頁。
- PDF 由 Pillow 的 `save(save_all=True, resolution=300)` 寫出，建立與修改時間固定為 2026-11-21 00:00 UTC，標題固定。在同一環境下重跑兩次，sha256 完全相同。
- 產出的 PDF：9 頁，A4（595.2 × 841.92 pt），1,797,650 bytes，**sha256 `b781737a3af684bacad22d81a54d47313812021226dbf85ced76fc82e2fdf30b`**。小於 2 MB，因此放在 repo 內。
- [run_real_scan_evaluation.py](run_real_scan_evaluation.py) 讀取一個資料夾，依檔名取得 01 到 09，比對 v4（rapidocr-onnxruntime 1.4.4 內附權重）與官方 PP-OCRv6 small ONNX。計分沿用 B3b 的 `normalized()`、`edit_distance()`，語言彙總沿用 B3b2 的 `language_totals()`，官方字表與雜湊核對沿用 B3b5 的 `official_check.py`。結果以 `'x'` 模式寫入新檔。

### 前處理方式的實驗（整頁 vs 墨跡裁切）

掃描會有旋轉、邊緣陰影與黑邊，因此比較了兩種做法：
- **page**：整張影像直接辨識（預設）。
- **trim**：以灰階小於 160 的墨跡範圍裁切（保留 2% 邊界），只作對照。

結果見下方乾跑表。整頁辨識在兩種條件下都較好，而且不依賴門檻值。墨跡裁切會因為陰影或雜點改變裁切範圍，也會改變影像的實際尺寸，因此不採用為預設。**限制**：真實掃描若邊緣有黑邊，整頁辨識可能讀出無關的雜訊字，這會直接反映在編輯數上。評估腳本會保留每頁的辨識文字與行數，方便人工檢查。

### 乾跑（不是真實掃描）

乾跑的目的只是確認流程可以走通、分數與 B3b2、B3b5 的同題結果相近。
- **clean**：PDF 以 pypdfium2 在 300 dpi 光柵化。pdfium 的寬度為 2481 px，比生成時的 2480 px 多 1 px。
- **scanlike**：對 clean 的每頁套用 B3b3 `degrade_scan.py` 的 `rotate 0.8`、`noise 10`、`jpeg 50`，每頁用固定種子。這只是參數模擬，**不等於真實掃描機或手機的成像**。

| 條件 | 前處理 | v4 編輯數（正確率） | v6 small 編輯數（正確率） |
| --- | --- | ---: | ---: |
| clean | page | 64（96.89%） | 10（99.51%） |
| clean | trim（對照） | 78（96.21%） | 9（99.56%） |
| scanlike | page | 231（88.78%） | 170（91.75%） |
| scanlike | trim（對照） | 339（83.54%） | 288（86.02%） |

參考字數合計 2060（與 B3b2 的 472＋470＋1118 相同）。clean 的 page 結果與 B3b2 的 v4 合計 72、v6 合計 13 相近，差異來自 300 dpi 光柵化與 1.7 倍放大。逐頁與語言細項見 [dry-run-summary.json](dry-run-summary.json)。

輸入驗證已測試三種錯誤情況：缺頁、檔名不符規則、只有後綴 `-phone` 而未指定 `--suffix`。三者都會明確停止並說明原因。

### 重現步驟

```bash
# 1. 產生 PDF（需要 repo 內 B3b2 的 samples 與 venv 中的 Pillow）
python make_scan_kit_pdf.py --output <repo 外的路徑>/real-scan-test-kit.pdf
# 2. 評估（需要官方 v6 ONNX 與 inference.yml，見 B3b5 README 的固定 commit）
python run_real_scan_evaluation.py --scan-dir <掃描資料夾> --suffix "" --mode page \
  --official-v6 <inference.onnx> --official-v6-yml <inference.yml> \
  --chars-dir <新的字表目錄> --output <新的結果 JSON>
```

官方 v6 的 `inference.onnx` 與 `inference.yml` 不放進 repo，請依 B3b5 README 的固定 commit `b8f84f0b…` 下載，並核對 SHA-256 `5435fd74…`（ONNX）與 `ab078671…`（yml）。
